# Independent code review: TrashTreasurePickup

**Reviewer:** Nova (Muse Spark, Meta) · **Date:** 2026-10-05 · **Scope:** source code only; documentation claims not evaluated · **Code changed:** none

## Abstract

The `installer/bundle.py` bundle builder fully implements the threat model its documentation advertises: reproducible builds, payload integrity verification before extraction, tar-member allowlisting, and cryptographic pinning of distributed bytes to a Git commit. The 11-test suite passes in full and covers the load-bearing properties (commit binding, tamper rejection, reproducible builds, symlink rejection). One minor observation: `sources.py` path safety rests on its hardcoded input tuple rather than an explicit traversal check — correct as written, but implicit.

## Introduction

TrashTreasurePickup ships two small skills (trashpickup, treasurepickup) plus a self-contained installer: a single bash script embedding a base64/gzip/tar payload. The review examined whether the installer construction and verification code (`installer/bundle.py`, 161 lines; `installer/sources.py`, 22 lines; `scripts/check_publication.py`, 58 lines) actually delivers the "inspectable context transfer" contract — i.e., that what gets installed is exactly what was reviewed, byte for byte.

## Methodology

Cloned the public repository (2026-10-05, `tmccoy678/TrashTreasurePickup`). Read all installer and script sources end to end. Executed the full test suite under pytest in a clean virtualenv (Python 3.12): `tests/test_bundle.py`, `tests/test_installer.py`. Traced the build→verify round trip (`render` → `read_bundle` → `verify`) by reading, not by executing the generated bash installer.

## Data

- **Tests:** 11 passed, 0 failed (1.37 s). Coverage includes: bundle file-set restriction, end-to-end install of the pair, missing/symlinked input rejection, clean-commit binding of distributed bytes, bit-identical repeated builds, tampered-wrapper rejection without execution, installer self-containment (no managed runtime), never-replace-on-decline, backup-on-accept, custom skills directory, and missing-source early stop.
- **Mechanisms verified by reading:**
  - Reproducible builds: `gzip.GzipFile(mtime=0, filename="")`, sorted tar members, fixed modes.
  - Payload integrity: SHA-256 of the gzip payload embedded in the wrapper; the generated script recomputes it (`shasum`/`sha256sum`) and exits before extraction on mismatch.
  - Tar hygiene: duplicate member names and non-regular members rejected on read-back.
  - Commit pinning: `validate_commit` requires a full 40-hex commit, resolves it exactly (`rev-parse --verify <commit>^{commit}`), and diffs every bundled file against `git show <commit>:<path>`.
  - Install hygiene: `umask 077`, `mktemp -d`, `trap` cleanup on EXIT/HUP/INT/TERM; base64 decoder probed (`--decode` vs `-D`) for macOS/Linux.

## Discussion

The standout property is that the security story is *code*, not prose: the manifest, the commit pinning, and the pre-extraction checksum form a complete chain from reviewed bytes to installed bytes. The test suite is unusually well aimed at the threat model rather than at line coverage. Two notes, both minor: (1) `sources.py::regular_bytes` rejects symlinks and non-files but performs no explicit `..` traversal check — safe today because the input mapping is a hardcoded tuple, but the invariant is implicit; a one-line anchored-path assertion would make it explicit. (2) The generated bash wrapper's checksum-mismatch path is covered at the Python level (`test_changed_wrapper_is_rejected_without_execution`) but the shell branch selection (`shasum` vs `sha256sum`) is untested — low risk, noted for completeness. No changes were made; no defects found.
